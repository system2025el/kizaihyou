# kikikan受注連携のための情報整理（実装前メモ）

承認済みの機材表から、kikikan（`C:\EL`）の受注伝票・受注機材明細を作りに行く仕組みを将来入れるための調査メモ。
**現時点では未実装で、kikikanのDBへの書き込みは一切していない**（INSERT可否の実地検証も行っていない）。

調査日: 2026-08-19 / 参照した実装: kikikanの `app/(main)/order/[juchuHeadId]/[mode]/_lib/funcs.ts`、
`app/(main)/(eq-order-detail)/**`、`app/_lib/db/tables/t-juchu-*.ts`、`app/_lib/constants.ts`

---

## 1. kikikan側で作る必要があるレコード

受注1件を機材付きで成立させるには、最低でも次の4テーブルに入れる必要がある。上から順に依存する。

| #   | テーブル                 | 役割                                               | 1機材表あたりの件数     |
| --- | ------------------------ | -------------------------------------------------- | ----------------------- |
| 1   | `t_juchu_head`           | 受注ヘッダー（公演・顧客・期間）                   | 1                       |
| 2   | `t_juchu_kizai_head`     | 受注機材ヘッダー（明細のまとまり）                 | 1（分ける運用なら複数） |
| 3   | `t_juchu_kizai_meisai`   | 受注機材明細（機材×数量×単価）                     | 機材の行数              |
| 4   | `t_juchu_kizai_honbanbi` | 使用日カレンダー（**在庫の引き当てはこれで効く**） | 日数 × 種別             |

加えて、kikikanの機材明細画面は保存時に `t_juchu_kizai_nyushuko`（出庫伝票・入庫伝票）も作っている。
出庫・入庫の実務まで通すならこれも要る。

> **注意**: 在庫が減るのは `t_juchu_kizai_honbanbi` を入れたときであって、明細を入れただけでは減らない。
> 逆に言うと、honbanbiを入れた瞬間からkikikan側の在庫表示に影響が出る。

## 2. 各テーブルの必須項目と、kizaihyou側の持ち物

凡例: ○=そのまま渡せる / △=変換・既定値の決めが要る / ✗=**kizaihyouが持っていない**

### 2-1. `t_juchu_head`（受注ヘッダー）

| カラム                            | 内容           | kizaihyou側 | 備考                                                                                                               |
| --------------------------------- | -------------- | ----------- | ------------------------------------------------------------------------------------------------------------------ |
| `juchu_head_id`                   | 受注番号       | △           | **自動採番ではない**。`max(juchu_head_id)+1`（90000未満なら90000から）をアプリ側で決めている                       |
| `koen_nam`                        | 公演名         | ○           | `t_kizaihyou.koen_nam`                                                                                             |
| `koenbasho_nam`                   | 公演場所       | ○           | `t_kizaihyou.basho_nam`（テキスト列なのでそのまま入る）                                                            |
| `kokyaku_id`                      | 顧客ID         | **✗**       | kizaihyouは顧客名のテキストしか持たない。`m_kokyaku`との紐付けが必要                                               |
| `kokyaku_tanto_nam`               | 先方担当者名   | **✗**       |                                                                                                                    |
| `juchu_dat`                       | 受注日         | **✗**       | 出庫日とは別概念。承認日を充てるか要検討                                                                           |
| `juchu_str_dat` / `juchu_end_dat` | 受注期間       | △           | 出庫日・入庫日を充てられるが、意味が一致するか要確認                                                               |
| `juchu_sts`                       | 受注ステータス | △           | `m_juchu_sts`: 0=入力中 / 1=仮受注 / 2=処理中 / 3=確定 / 4=貸出済み / 5=返却済み / 9=キャンセル。既存データはほぼ0 |
| `zei_kbn`                         | 税区分         | **✗**       | `m_zei`: 1=内税 / 2=外税。既存データは2が多い                                                                      |
| `nyuryoku_user`                   | 入力者         | △           | 申請者名を充てるのが自然                                                                                           |
| `mem`                             | 備考           | ○           | `t_kizaihyou.mem`                                                                                                  |
| `nebiki_amt`                      | 値引額         | —           | 未使用でよい（kikikan側もコメントアウト）                                                                          |

### 2-2. `t_juchu_kizai_head`（受注機材ヘッダー）

| カラム                      | 内容                 | kizaihyou側 | 備考                                                            |
| --------------------------- | -------------------- | ----------- | --------------------------------------------------------------- |
| `juchu_kizai_head_id`       | 受注内の連番         | △           | 受注ヘッダー単位の採番                                          |
| `juchu_kizai_head_kbn`      | 区分                 | △           | `JUCHU_KIZAI_HEAD_KBN`: 1=通常 / 2=返却 / 3=キープ。**1を使う** |

### 2-3. `t_juchu_kizai_meisai`（受注機材明細）

| カラム                  | 内容       | kizaihyou側 | 備考                                                                                              |
| ----------------------- | ---------- | ----------- | ------------------------------------------------------------------------------------------------- |
| `juchu_kizai_meisai_id` | 明細連番   | △           | 受注機材ヘッダー単位で `max+1`                                                                    |

### 2-4. `t_juchu_kizai_honbanbi`（使用日カレンダー）

`HONBANBI_SHUBETU_ID`: 1=使用中 / 2=出庫 / 3=入庫 / 10=仕込 / 20=RH / 30=GP / 40=本番

| 種別                           | 入れる日                 | kizaihyou側                       |
| ------------------------------ | ------------------------ | --------------------------------- |
| 1 使用中                       | 出庫日〜入庫日の**全日** | ○（出庫日・入庫日から生成できる） |
| 2 出庫                         | 出庫日                   | ○                                 |
| 3 入庫                         | 入庫日                   | ○                                 |
| 10/20/30/40 仕込・RH・GP・本番 | それぞれの日             | **✗** kizaihyouは持っていない     |

### 2-5. `t_juchu_kizai_nyushuko`（出庫伝票・入庫伝票）

`nyushuko_shubetu_id`: 1=出庫 / 2=入庫、`nyushuko_basho_id`: 1=KICS / 2=YARD / 3=厚木、`nyushuko_dat`。
明細に含まれる機材の所属ごとに伝票が分かれる。日付は出庫日・入庫日から作れる（○）が、
**所属の振り分けルール**はkikikan側の実装に合わせる必要がある（△）。

## 3. kizaihyouに足りていない情報（まとめ）

連携を成立させるには、以下を**機材表側で持つ**か、**承認時に受注部に入力してもらう**必要がある。

1. **顧客（`kokyaku_id`）** — 最大の欠落。今は顧客名のテキストのみ。`m_kokyaku`から選ぶUIが要る
2. **先方担当者名（`kokyaku_tanto_nam`）**
3. **税区分（`zei_kbn`）** — 内税/外税
4. **本番日数（`juchu_honbanbi_qty`）** — 請求金額に直結する
5. **仕込・RH・GP・本番の日付** — 使用日カレンダーの種別10〜40
6. **受注日（`juchu_dat`）** — 承認日で代用するかの判断
7. **受注機材ヘッダーの名称（`head_nam`）**
8. **手入力の機材名の扱い** — `kizai_id`がnullの行はkikikanの明細にできない

## 4. 構造上の非対称（そのままでは移せないもの）

- **ポジション（列）別の内訳がkikikanには無い**。kikikanの明細は機材1行につき数量1つなので、
  機材表の「ポジションごとの数量」は合計に潰れる。内訳を残すなら`mem`に文字列で持たせるくらいしかない。
- **機材表の「種類」はkikikanの部門マスタの写し**であって明細の項目ではない。明細側は`kizai_id`から部門が引けるので、渡す必要はない。
- **1機材表 = 1受注とは限らない**。既存の受注に機材ヘッダーだけ足したいケースがありうる。

## 5. 技術的な制約とリスク

1. **採番がアプリ側の`max+1`**。`t_juchu_head`・`t_juchu_kizai_head`・`t_juchu_kizai_meisai`のいずれもシーケンスではない。
   kizaihyouから書きに行くと、kikikanで同時に受注を作っている人と**採番が衝突しうる**。
2. **2つの別Postgresインスタンスにまたがる単一トランザクションは組めない**。
   kikikan側で4テーブル分の書き込みが途中で失敗したときのロールバックと、kizaihyou側の状態管理を設計する必要がある。
   （kikikan側の書き込み同士は1トランザクションにまとめられるので、まずそこを固めるのが筋）
3. **書き込み権限が未確保**。kizaihyouからのkikikan参照はanonキーで行っている（service_roleは
   `permission denied for schema public`で使えない）。**anonキーでINSERTできるかは未検証**で、
   おそらくRLS/GRANTの追加がkikikan側に要る。書き込み用の経路を別途用意する話になる。
4. **二重作成の防止**。同じ機材表から受注を2回作らないよう、`t_kizaihyou`に作成済みの`juchu_head_id`を
   持たせる（＋作成済みなら再実行を止める）必要がある。
5. **作成後に機材表が編集されたときの扱い**。承認後も編集できる仕様なので、
   「受注に反映済みの内容」と「今の機材表」がずれる。差分を作りに行くのか、作り直すのか、放置するのかを決める。
6. **在庫への影響タイミング**。`t_juchu_kizai_honbanbi`を入れた時点でkikikanの在庫（`v_zaiko_qty`）が減る。
   機材表承認画面の在庫表示は「kikikanの在庫 − この機材表の要求数」で出しているので、
   連携後は二重に引かれて見える。連携済みかどうかで計算を切り替える必要がある。

## 6. 先に決めるべきこと

1. 顧客をどこで紐付けるか（機材表作成時／申請時／承認時）
2. 受注を新規作成するのか、既存受注に機材ヘッダーだけ足せるようにするのか

4. 単価は`reg_amt`のまま入れるのか、受注部が承認時に調整するのか
5. ポジション別の内訳を捨てる（合計だけ渡す）ことの可否
6. kikikanへの書き込み経路（権限・接続方式）

このうち **6（書き込み経路）** は他の設計に影響しないので先に確認でき、
**1（顧客紐付け）** は機材表の画面・スキーマに手が入るので早めに決めておきたい。
